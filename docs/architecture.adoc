== Overview

Family Tree is a static web application for managing genealogy data in the browser.
It is built with plain HTML, CSS, and JavaScript, and is deployed as static files.

Most application data stays local to the browser:

* family data and UI state live in `localStorage`
* uploaded images live in `IndexedDB`
* geocoding results are cached in `localStorage`

The application is not fully offline-only.
The sample dataset is fetched on first load, and the map feature uses OpenStreetMap tiles plus Nominatim geocoding when a place does not already have stored coordinates.

== Goals and Constraints

* **Readable code**: keep files small and responsibilities clear
* **Static deployment**: no backend, no server-side rendering
* **Portable data**: JSON and ZIP import/export
* **Browser storage first**: family records remain local unless the user exports them
* **Framework-free UI**: plain DOM APIs and a few vendored libraries

=== Responsibilities

|===
| File | Responsibility

| `index.html`
| Static shell, panels, controls, and modal markup

| `js/app.js`
| Bootstrap, family switching, import/export, tab events, toast messages

| `js/storage.js`
| `localStorage` persistence for families and family datasets

| `js/images.js`
| `IndexedDB` storage for uploaded photos

| `js/list.js`
| Searchable list rendering

| `js/modals.js`
| Modal open/close behavior, detail view, person editing, shared formatting helpers

| `js/tree.js`
| Tree controller: reads UI state and triggers rendering

| `js/tree-graph.js`
| Tree graph selection and layout building for descendants, ancestors, and force mode

| `js/tree-renderer.js`
| D3 rendering, zooming, node drawing, and force simulation lifecycle

| `js/map.js`
| Leaflet map setup, marker rendering, geocoding, and popup behavior
|===

== Build and Dependencies

The repository vendors browser dependencies into `js/vendor/` during the build step.
This keeps deployment simple while avoiding runtime CDN dependencies.

=== Build command

[source,bash]
----
npm ci
npm run build
----

=== Vendored libraries

* `d3`
* `jszip`
* `leaflet`
* `leaflet.markercluster`

`build.js` copies the required files from `node_modules` into `js/vendor/`.

== Data Model

=== Family registry

Two `localStorage` keys manage the available datasets:

|===
| Key | Purpose

| `familyTree_families`
| List of `{id, name}` family entries

| `familyTree_active`
| Currently selected family id
|===

Each family dataset is stored under `familyTree_data_{id}`.

=== Family dataset

[source,json]
----
{
  "persons": [...],
  "partnerships": [...]
}
----

=== Person

[source,json]
----
{
  "id": "uuid-or-string",
  "name": "Full Name",
  "birthDate": "YYYY-MM-DD",
  "deathDate": "YYYY-MM-DD",
  "description": "Optional notes",
  "image": "Optional http(s) URL or data URI",
  "parents": [
    { "personId": "p1", "type": "mother" },
    { "personId": "p2", "type": "father" }
  ],
  "places": [
    { "type": "birth", "name": "Hamburg, Germany" }
  ]
}
----

=== Partnership

[source,json]
----
{
  "id": "uuid-or-string",
  "person1Id": "p1",
  "person2Id": "p2",
  "type": "marriage | divorced | partner",
  "startDate": "YYYY-MM-DD",
  "endDate": "YYYY-MM-DD"
}
----

The canonical export shape is described in `data/family-tree.schema.json`.

== Tree Rendering

Tree rendering is split into two layers.

=== Controller layer (`js/tree.js`)

The controller:

* reads the selected mode, root person, and depth
* validates that the current family can be rendered
* requests a render graph from `js/tree-graph.js`
* passes the result to `js/tree-renderer.js`

=== Graph layer (`js/tree-graph.js`)

This layer decides which people and relationships belong in the current view and computes positions where needed.

Supported modes:

* **Descendants**: build a D3 hierarchy rooted at the selected person and include current partners
* **Ancestors**: collect parents up to the selected depth, include nearby descendants for context, then build a layered layout
* **Force**: build a relationship graph for D3 force simulation

=== Renderer layer (`js/tree-renderer.js`)

This layer owns:

* SVG initialization
* zoom behavior
* parent/child and partnership link drawing
* node rendering, labels, and photo clip paths
* force simulation setup and teardown
* viewport fitting for non-force layouts

== Map Rendering

The map is optional and external-service-backed.

When the map tab is opened:

. Leaflet initializes the map container once.
. The app gathers `places` from the active family.
. Stored coordinates are reused immediately.
. Missing coordinates are geocoded through Nominatim.
. Successful geocodes are cached and written back into family data.
. Markers are clustered with `leaflet.markercluster`.
. Co-located clusters with 8 or fewer people are auto-expanded after the map settles.

External requests made by the map feature:

* OpenStreetMap tile requests
* Nominatim geocoding requests

== Import and Export

=== Import

Imports support:

* raw JSON pasted into the modal
* `.json` files
* `.zip` files containing `family.json` and optional `images/`

ZIP imports are unpacked in the browser with JSZip.
Image blobs are stored in `IndexedDB` after the new family is created.

=== Export

Exports support:

* pretty-printed JSON
* ZIP bundles containing `family.json` plus extracted image files

== Storage Strategy

|===
| Storage | Contents

| `localStorage`
| family registry, active family id, family datasets, geocode cache

| `IndexedDB`
| uploaded person photos
|===

This split keeps structured family data simple while moving large binary files out of `localStorage`.

== Security and Privacy Notes

* User-provided image URLs are sanitized before use
* Imported JSON is parsed with `JSON.parse()`
* User text is inserted with DOM text APIs, not executed as HTML
* Inline event handlers are avoided; UI events are wired in JavaScript
* Map mode is the main exception to the app's local-first behavior because it talks to OpenStreetMap services

== Deployment

The GitHub Actions Pages workflow:

. checks out the repository
. installs dependencies with `npm ci`
. runs `npm run build`
. uploads the repository root as the Pages artifact
. deploys with `actions/deploy-pages`

A manual deployment should follow the same build steps before publishing static files.
